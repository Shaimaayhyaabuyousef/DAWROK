# تطبيق مخطط DAWROK على Firestore

هذا التحديث يكيّف العلاقات مع التطبيق الحالي، ولا يستبدل منطق التسجيل أو الحجز بمخطط جديد. أسماء الحقول الحالية محفوظة لتفادي كسر التطبيق. معرّف مستند Firestore هو المفتاح الأساسي؛ المسار المتداخل يمثل جزءاً من العلاقة.

## ثوابت لم تتغير

- الدخول بالبريد الإلكتروني وكلمة المرور من Firebase Authentication. لا تخزين لـ `password_hash` أو كلمة المرور أو PIN في Firestore.
- مراحل إنشاء حساب المواطن والتحقق التجريبي والحقول المطلوبة كما هي. إنشاء المنشأة من الإدارة ودعوة الموظف بالكود ثم الموافقة كما هما. لا تحويل للهاتف إلى وسيلة دخول ولا فرض حقول تسجيل إضافية.
- المواطن لا يختار الوقت: يؤكد الحجز فيحسب النظام رقم الدور وفترة الوصول تلقائياً ضمن آلية النصف ساعة القائمة.
- طابور واحد مشترك، بلا نوافذ أو بعدة نوافذ. الموظفون يوزعون على الشواغر. المنشأة تدير جميع الطوابير والنوافذ سواء وُجد موظفون أم لم يوجدوا.
- قواعد +5 للحضور و-5 للغياب، التقييد بعد الغياب المتكرر، واستبدال 100 نقطة بمقعد إضافي بعد نفاد السعة أو بأولوية داخل الفترة، كلها محفوظة.

## مقابلة كيانات المخطط

| الكيان | الموقع في المشروع | العلاقة والضبط |
|---|---|---|
| USERS | Firebase Auth + `users/{uid}`، وللموظف `staff_profiles/{uid}` و`staff_memberships/{uid}` | UID موحد للهوية. البريد والدور وملف الحساب لم تُنقل أو تُعدّل. الصلاحيات الإدارية من custom claims الموثوقة. |
| CITIZENS | `citizen_identity/{uid}` و`citizen_accounts/{uid}` | الهوية خاصة بالمواطن، والرصيد والقيود لا يعدلهما المواطن بحرية. |
| FACILITIES | `facilities/{fid}` | `ownerUid` يربط حساب المنشأة، مع مطابقة `users/{uid}.facilityId`. الإنشاء الإداري الحالي محفوظ. |
| SERVICES | `facilities/{fid}/services/{sid}` | خدمة تابعة لمنشأة واحدة. الطابور الجديد يحمل `serviceId` وتتحقق القواعد من مرجعه واسمه ونشاطه. |
| QUEUES | `facilities/{fid}/queues/{qid}` | معرّف المنشأة مضمن في المسار. `serviceId` مرجع مستقل، و`schemaVersion: 3` يميز العلاقات الجديدة. |
| COUNTERS | `facilities/{fid}/counters/{qid}_{window}` | وثائق مستقلة باسم النافذة ومكانها وحالتها. تحقق من الطابور وحدود عدد النوافذ. لا نافذة مصطنعة للطابور ذي العدد صفر. |
| STAFF | `facilities/{fid}/staff/{sid}` + `staff_memberships/{uid}` | المطابقة عبر UID وstaffId والمنشأة. التكليف الحالي في `operations/assignments` وصلاحيته تتحقق مجدداً عند العمل. |
| STAFF_LINK_CODES | `staff_invites/{hash}` + `staff_join_requests/{hash}` | رمز الدعوة وانتهاؤه واستخدامه والموافقة مترابطة ذرياً، كما في السيناريو السابق. |
| BOOKINGS | `bookings/{bid}` | معرّف المستند رقم تذكرة فريد، و`queuePosition` رقم الدور اليومي. `slotStart` الموعد التلقائي. تطابق المنشأة والطابور والخدمة والمواطن يمنع المراجع المصطنعة. |
| POINT_TRANSACTIONS | `citizen_accounts/{uid}/point_transactions/{id}` | سجل مستقل مرتبط بالحجز، غير قابل للتعديل أو الحذف. تحديث الرصيد والاستبدال/نتيجة الخدمة وحركة النقاط يتم معاً. |
| SCAN_LOGS | `facilities/{fid}/queue_logs/{id}` | `bookingId` الكامل + `actorUid` + `actorRole` + `staffId` للموظف. صاحب المنشأة ليس موظفاً وهمياً؛ staffId فارغ له. لمحاولة QR غير صالح bookingId فارغ لأن الحجز قد لا يوجد. |
| NOTIFICATIONS | `citizen_accounts/{uid}/events/{id}` و`users/{uid}/notifications/{id}` | إشعارات صاحب الحساب فقط. يغير المستلم علامة القراءة وحدها. الإشعار الإداري يحمل senderId موثقاً؛ إن ذكر حجزاً فيجب أن يخص المستلم. |
| REPORTS | `reports/{id}` | المواطن يبلغ عن التطبيق أو منشأة فعلية؛ المنشأة والموظف عن التطبيق فقط. الهوية والصلاحيات الحالية محفوظة. |
| ADMIN_AUDIT_LOGS | `admin_audit_logs/{id}` | قراءة للإدارة وسجل إضافي غير قابل للتعديل/الحذف من العملاء. المهام الموثوقة عبر Admin SDK تسجل principal حساب الخدمة بدلاً من اختلاق UID إداري. |

## اختلافات مقصودة عن الرسم

1. العلاقة QUEUES → COUNTERS أصبحت واحداً إلى صفر/عدة، وفق آخر سيناريو متفق عليه. `counter_id` وحيد في الطابور لا يكفي. رقم `windowNumber` القديم في مستند الطابور يبقى رقم الطابور الداخلي، وليس عدد نوافذه.
2. QR يحمل مرجع الحجز الحالي ويُفحص في Firestore؛ لا يُعامل رمز QR وحده كإذن لتجاوز صلاحيات الحساب أو حالة التذكرة.
3. `standing` يستنتج من الرصيد والقيود الحالية، ولا يقبله النظام كقيمة يقررها المواطن.
4. `must_change_password` غير مفروض لأن فرضه يغير تفاصيل إنشاء الحسابات الحالية. كلمات المرور تظل في Authentication.
5. العلامتان UK للهاتف والهوية في الرسم **ليستا قيدي تفرد عالميين مفعلين بهذا التحديث**. أبقينا شروط التسجيل كما طلب المستخدم؛ إضافة قيد رفض جديد تتطلب معالجة السجلات المكررة وترحيل فهرس تفرد أولاً. أداة الترحيل تعرض عدد التكرارات دون كشف القيم أو تغيير الحسابات. تفرد البريد توفره آلية Authentication الحالية.
6. `created_by` للمنشآت التاريخية غير معروف دائماً؛ لا تُختلق هوية منشئ لتعبئة الرسم. مسار إنشاء المنشأة الإداري الحالي لم يتغير.

## الترحيل والتوافق

الأداة `scripts/migrate_erd_relations.mjs` تعمل بوضع القراءة فقط افتراضياً. تنشئ عند التطبيق مراجع الخدمات وبيانات النوافذ للطوابير القديمة. لا تحذف بيانات ولا تعيد ترتيب الحجوزات ولا تغير الحسابات أو كلمات المرور أو النقاط أو تكليف الموظفين. تتوقف قبل الكتابة عند اكتشاف تعارضات في بيانات المراجع. التنفيذ على عدة طوابير ليس معاملة عالمية واحدة؛ يمكن إعادة تشغيله بعد انقطاعه.

```powershell
# ملف الاعتماد يبقى خارج المشروع، ولا يُرفع إلى GitHub.
$env:GOOGLE_APPLICATION_CREDENTIALS = 'C:\private\dawrok-service-account.json'
node scripts/migrate_erd_relations.mjs
# بعد مراجعة نتيجة القراءة فقط:
node scripts/migrate_erd_relations.mjs --apply
firebase deploy --only firestore:rules --project dawrok-f908e
flutter run -t lib/pages/main.dart
```

ينبغي تحديث تطبيقات الأدوار الثلاثة مع القواعد. الطوابير القديمة تظل قابلة للقراءة والحجز بالآلية السابقة حتى ترحيلها أو تحريرها بالتطبيق الجديد. تعديل طابور من التطبيق الجديد ينشئ مراجع الخدمة والنوافذ معه في معاملة واحدة. تغيير السعة/المواعيد/عدد النوافذ يحتفظ بضوابط الحجوزات الحالية.

حركات النقاط التاريخية لا تُختلق ولا تُعاد محاسبتها؛ يبقى الرصيد السابق، ويسجل كل استبدال أو نتيجة خدمة جديدة في السجل المستقل. سجلات المسح القديمة تظل مقروءة، والسجلات الجديدة تتطلب المنفّذ الحقيقي ومرجع الحجز.

قواعد Firestore لا تنفذ ترحيلاً تلقائياً ولا تسري على Admin SDK؛ لذلك الأداة تتحقق من العلاقات صراحة وتسجل تنفيذ الترحيل. لا توجد Cloud Functions جديدة ولا تعديل لخطة Spark.

## رقم المنشأة والتوظيف

يصدر النظام رقمًا ثابتًا من ست خانات يبدأ من 100000. للمنشأة الجديدة يستخدم السكربت الرقم نفسه كمعرّف مستندها. تحصل المنشأة السابقة على حقل facilityNumber داخل مستندها الحالي حتى تظل مراجع الحجوزات والموظفين صالحة. رقم المنشأة عام، ورمز دعوة الموظف خاص ومؤقت.

لتحديث المنشآت السابقة، استخدمي اعتماد الإدارة نفسه كما في ترحيل العلاقات أعلاه، ومن جذر المشروع شغلي:

```powershell
node scripts/migrate_facility_numbers.mjs
node scripts/migrate_facility_numbers.mjs --apply
```

راجعي اسم المشروع وعدد المنشآت في المعاينة قبل التطبيق. يمكن إعادة التنفيذ بعد انقطاعه. بعد الترقيم انشري قواعد Firestore وشغلي نسخة التطبيق المحدثة للمنشأة والموظف معًا. تتطلب الطلبات الجديدة الرقم في القواعد المحدثة. طلبات التوظيف المرسلة سابقًا قابلة للمراجعة، والدعوات السارية تستخدم رقم المنشأة عند تقديم الطلب. يعرض ملف المنشأة الرقم مع زر نسخ، وتعرضه نافذة إصدار الدعوة أيضًا.
