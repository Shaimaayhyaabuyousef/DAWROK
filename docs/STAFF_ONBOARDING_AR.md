# DAWROK — ربط حساب الموظف بالمنشأة

## التدفق الكامل
1. يسجّل صاحب المنشأة الدخول بحسابه الذي أنشأه Admin، ويفتح Staff > Add Staff Member.
2. يملأ اسم الموظف، رقم الموظف، المهمة، والنافذة، ثم يضغط Generate Link Code.
3. يُنشئ Firebase مستند الموظف `facilities/{fid}/staff/{id}` ومستند الدعوة `staff_invites/{sha256}` بعملية batch واحدة.
4. تظهر نافذة بالرمز وزر Copy عند الإنشاء، ثم يُعرض الرمز على بطاقة الموظف حتى بعد إغلاق النافذة. صلاحية الدعوة 24 ساعة. تحفظ بصمة SHA-256 في staff_invites، والنص مؤقتًا في مستند الموظف المحمي بقراءة صاحب المنشأة فقط، ويُحذف عند الموافقة أو الرفض.
5. من شاشة Login العامة يضغط الموظف **Employee Sign In** للدخول المعتاد بالبريد وكلمة المرور فقط. إذا كان جديدًا يختار **New employee? Request to Join Facility**؛ يُدخل Facility ID ورمز الدعوة والهاتف، ثم ينشئ حساب Firebase Auth بالبريد وكلمة المرور (أو يختار Existing account إذا كان لديه حساب). رمز الدعوة لا يُطلب في تسجيل الدخول المعتاد.
6. يتحقق التطبيق من الرمز، ويخزن `staff_join_requests/{sha256}` بحساب Firebase Auth الخاص بالموظف.
7. تعكس شاشة الموظفين لدى المنشأة طلبًا حقيقيًا مع Accept / Reject، وليس مجرد موافقة شكلية.
8. عند Accept تكتب معاملة ذرية: staff state active + join approved + invite redeemed + `staff_memberships/{uid}` active.
9. حالة الانتظار/الرفض/القبول محفوظة في Firestore. الموظف يستطيع إغلاق التطبيق والعودة وتسجيل الدخول ببريده وكلمة مروره فقط؛ Splash يعيد توجيهه حسب الحالة.
10. أول مرة بعد الموافقة يفرض `employee_profile_screen` إدخال الاسم الكامل والهاتف والعنوان ورقم الطوارئ. قواعد Firestore تمنع الوصول لتذاكر العمل قبل حفظ هذه البيانات.
11. بعد اكتمال الملف يدخل إلى `employee_home_screen` ويستطيع تصفح التذاكر، الاستدعاء، التأجيل، إنهاء الخدمة والتحقق اليدوي من رقم التذكرة/QR وفق دوره. وظيفة الكاميرا التلقائية غير مربوطة بعد.

## مهم عند تجربة الحسابات
- لا تستخدم بريد حساب المواطن أو المنشأة لإنشاء حساب الموظف؛ حساب الموظف في Firebase Auth منفصل، ولا يُسمح لحساب citizen بالمطالبة بالدعوات.
- لا يمنح رمز الدعوة أية صلاحيات عمل. يجب إنشاء حساب الموظف، ثم تقديم الطلب، ثم قبول المنشأة، ثم إكمال الملف.
- الأكواد طويلة وعشوائية، وتظل على بطاقة الموظف بصفة مؤقتة لحساب صاحب المنشأة فقط، حتى الموافقة أو الرفض. عند انتهاء الرمز أو رفض الطلب يمكن للمنشأة إصدار رمز جديد.
- تسجيل دخول موظف اعتمد سابقًا لا يحتاج إلى إبقاء شاشة الانتظار مفتوحة.
- يخضع التحقق من عضوية الموظف والصلاحية لدوال قواعد Firestore، لا لواجهة Flutter وحدها.
- تم الحفاظ على تصميم شاشة Add Staff والبطاقة الجاهزة للكود، وأضيف زر الدخول الجديد في الشاشة العامة.
- شاشات عمل الموظف في الفرع هي أساس وظيفي؛ يمكن مواءمة التفاصيل البصرية للشاشات المرجعية النهائية لاحقًا.

## نشر القواعد المحدثة (ضروري)
القواعد المنشورة سابقًا تمنع مجموعات الموظفين الجديدة. انسخ قواعد الفرع المحدّثة إلى Firebase Console > Firestore Database > Rules ثم Publish، أو استخدم:
```bash
firebase deploy --only firestore:rules --project dawrok-f908e
```
قبل النشر: خذ نسخة احتياطية من القواعد الحالية. نجاح GitHub Actions في المحاكي يختبر نموذجًا محليًا وليس مشروع Firebase الحقيقي.

## مثال حالات الموظف
| الحالة | وصول الموظف |
| --- | --- |
| invited | المنشأة أصدرت الرمز؛ الموظف لم يطلب الانضمام |
| requested | ينتظر موافقة المنشأة |
| rejected | الدخول محظور، ويمكن إصدار رمز جديد |
| approved + ملف غير مكتمل | يوجَّه لإكمال الملف إجبارياً |
| approved + ملف مكتمل | ينتقل لواجهة العمل |
| suspended | دخول الوظائف محظور، والبيانات تبقى محفوظة |

## الاختبارات المطلوبة قبل الإطلاق
- إضافة موظف: الرمز يظهر فور نجاح Batch وتظهر الدعوة في Firestore.
- رمز غير صحيح، منتهي أو مستعمل: الرفض ولا تُمنح عضوية.
- قبول/رفض: لا تُنشأ عضوية عند الرفض؛ عند القبول فقط.
- مغادرة التطبيق وإعادة تسجيل الدخول أثناء الانتظار وبعد القبول.
- إكمال ملف الموظف لأول مرة، ثم اختبار تسجيل الدخول التالي دون إعادة إلزامه.
- اختبار إيقاف الموظف من المنشأة وفقدان صلاحية العمليات فورًا.
- مراجعة الصلاحيات الدقيقة حسب الدور والمنشأة وتحديد إمكانية عرض معلومات المواطنين.
