# تدفّق الموظف — DAWROK

## من إضافة الموظف إلى العمل

1. تدخل المنشأة بحسابها المجهز من المسؤول (Admin) ثم تفتح Staff > Add Staff.
2. تُدخل الاسم والدور ورقم الموظف والشباك، ثم تضغط Generate Link Code. يُنشأ سجل الموظف في facilities/{fid}/staff/{staffId} مع رمز عشوائي **20 محرفًا** مقسّمًا كل أربعة محارف، وصلاحيته 24 ساعة. يظهر الرمز في البطاقة الأصلية ويدعم Copy. تظهر نافذة منبثقة تحتوي رمزًا قابلًا للنسخ؛ وبعد إغلاقها تظهر بطاقة الموظف مع نفس الرمز وزر نسخه، حتى بعد تحديث الشاشة. يحفظ Firestore البصمة SHA-256 في staff_invites/{hash}، كما يحتفظ مؤقتًا بالرمز النصي داخل مستند الموظف المسموح لصاحب المنشأة فقط بقراءته؛ ويُحذف من المستند عند الموافقة أو الرفض. يجب استخدام قناة موثوقة لمشاركة الرمز.
3. في صفحة Login الرئيسية، زر Staff Login / Staff Invitation يفتح شاشة Employee Join الجديدة طبقًا للمرجع. يدخل الموظف **معرّف المنشأة الفعلي من Firestore** والرمز ورقم هاتفه. معرّف المنشأة ليس الاسم ولا مثال FAC-8842 في الصورة المرجعية.
4. ينتقل الموظف لخطوة إنشاء حسابه في Firebase Authentication بواسطة البريد وكلمة المرور. يتم التحقق من الرمز وكونه من المنشأة المحددة ومن صلاحيته قبل كتابة staff_join_requests/{hash} (status=requested). رمز الدعوة لا يشكّل كلمة مرور ولا يمنح أي صلاحية عمل قبل موافقة المنشأة.
5. تظهر منشأة الموظف طلب Accept أو Reject في شاشة Staff. تؤدي الموافقة إلى إنشاء staff_memberships/{employeeUid} وربطه بمنشأة ودور وشباك محددين في معاملة ذرية، مع تغيير حالة الدعوة والطلب وبيانات الموظف. لا تكفي إضافة موظف وحدها للوصول إلى النظام.
6. لا يلزم إبقاء شاشة الانتظار أو التطبيق مفتوحين؛ الطلب والموافقة محفوظان في Firestore. عند الدخول لاحقًا بالبريد وكلمة المرور تُقرأ حالة الطلب/العضوية.
7. عند الموافقة الأولى يفرض المسار employee_profile_screen إكمال الاسم الكامل والهاتف والعنوان ورقم اتصال الطوارئ، ثم ينتقل إلى employee_home_screen. تمنع Firestore Rules الاطلاع على بيانات العمل قبل إكمال الملف.
8. شاشة Home تستعرض المنشأة والطوابير الحقيقية والإحصاءات، وScanner يدعم QR والكود اليدوي ويقرأ سجلات التشغيل من Firestore، كما في الصور المرجعية. صلاحيات عمليات الطوابير محصورة بموظف windowOfficer أو supervisor.

## تجهيز وتشغيل

- سحب آخر تغييرات الفرع: git pull --ff-only origin feature/firebase-facilities-queues-bookings
- تثبيت المكتبات: flutter pub get
- فحص: flutter analyze
- تشغيل: flutter run -d chrome -t lib/pages/main.dart
- افتح Firestore Console > Rules أو نفّذ firebase deploy --only firestore:rules --project dawrok-f908e **بعد مراجعة واختبار القواعد**. تحديث كود GitHub لا ينشر القواعد تلقائيًا.
- اختبر حساب المنشأة والموظف في متصفحين مختلفين أو في نافذة خفية؛ تسجيل موظف جديد في نفس المتصفح يغيّر جلسة Firebase الحالية.

## اختبارات يدوية

- رمز خاطئ أو من منشأة مختلفة: يجب رفض الربط.
- الرمز منتهي الصلاحية أو مستخدم: يجب رفض إنشاء طلب جديد.
- يظل الحساب Pending حتى موافقة المنشأة، ويُحفظ الطلب لو أغلق التطبيق.
- رفض الطلب يمنع وجود عضوية نشطة؛ يجب إصدار رمز جديد للمحاولة مجددًا.
- بعد الموافقة يتجه الموظف إلى إكمال الملف أولًا، ولا يمكن تخطيه إلى بيانات الطوابير.
- بعد إكمال الملف يمكن العودة والدخول دون رمز الربط.
- تعطيل الموظف يمنع صلاحيات العمليات عبر Firestore Rules.

## ملاحظات أمان

- حقل Facility ID يقبل ID المستند الفعلي في Firestore حاليًا وليس رمزًا قصيرًا للمستخدم. يمكن لاحقًا اعتماد كود منشأة عام مع تحقق آمن في backend.
- إضافة الملف الشخصي صورة المستخدم إلى Firebase Storage **غير منفذة**؛ يظهر مكان صورة محايد بدل صورة وهمية، ومناسب لاختبار Spark دون رفع هويات.
- قواعد Firestore واختبار Emulator نقطة انطلاق وليست تدقيقًا أمنيًا شاملًا. لا تعتبر بيانات employeeId وnationalId توثيقًا رسميًا للهوية، ولا تُرسل بيانات حقيقية أثناء الاختبارات.
- لا تُدمج Pull Request المسودة حتى اختبار الواجهات على Web وAndroid، والتحقق من التزامن والأدوار.

## إظهار رمز الربط على بطاقة الموظف
- عند إضافة موظف جديد، تضغط المنشأة Generate Link Code، فيظهر Popup مع زر Copy Code.
- بعد إغلاق الـPopup، يُعرض الرمز نفسه في Card الموظف داخل Staff (ما دام طلبه بانتظار الاعتماد). يمكن نسخه مباشرة من البطاقة أو توليد رمز بديل.
- الرمز صالح 24 ساعة؛ يظهر تنبيه إذا انتهت المدة. الرمز المنتهي لا يسمح بطلب جديد.
- الرموز المُنشأة قبل هذا التحديث لم تُحفظ بصيغتها النصية. استخدم New Code لإصدار رمز جديد؛ لا يمكن اشتقاق النص الأصلي من بصمة SHA-256.
- بسبب شرط استمرار إظهار النص حتى بعد إعادة تشغيل التطبيق، يصبح النص متاحًا في مستند Firestore الخاص بصاحب المنشأة، ومحمياً بقواعد القراءة للمالك وحده. هذه آلية مناسبة للنسخة التجريبية وليست بديلاً عن إدارة الأسرار في خادم موثوق للاستخدام الإنتاجي.
